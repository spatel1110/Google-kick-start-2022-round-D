2.1 RAG Kya Hai — Poori Kahani

Ek senior engineer ki taraf se — "RAG wo cheez hai jo LLMs ko hallucination se bachata hai. Production mein bina RAG ke LLM deploy karna = bina helmet ke bike chalana."

Problem before RAG: Dekh bhai, LLMs jaise GPT-4, Claude — yeh sab training data tak hi limited hain. September 2021 ke baad kya hua? Inhe pata nahi. Teri company ka internal documentation? Inhe pata nahi. Aur sabse bada issue — jab inhe answer nahi pata, yeh bahut confidently GALAT answer dete hain. Isko kehte hain hallucination. Production mein yeh acceptable nahi hai. Imagine kar — ek healthcare chatbot patient ko galat medicine suggest kar de. Ya ek legal bot galat clause cite kar de. Disaster!

Core Idea: RAG ka fundamental idea simple hai — LLM ko apni "yaaddaasht" pe depend mat karne do. Instead, relevant information RETRIEVE karo aur uske saath answer GENERATE karo. Matlab Retrieval + Augmented + Generation. Tu exam hall mein jaata hai na — agar open book exam hai toh tu answers BOOK se dhundh ke likhta hai. LLM ki book = tera Vector Database.

Exact Data Flow (6 Steps with Internal Details):

  1. User query aati hai — "What is our refund policy for international orders?" — yeh raw text hai
  2. Query embed hoti hai — Same embedding model jo documents ke liye use hua tha, wahi query pe bhi chalao. Output: [0.023, -0.156, 0.891, ...] ek 1536-dimensional vector
  3. Vector DB mein similarity search — Query vector ko stored document vectors ke saath compare karo. HNSW algorithm se nearest neighbors milte hain in milliseconds. "Kaun se stored documents isse milte-julte hain?"
  4. Top-k relevant chunks milte hain — best 3-5 matching pieces of text with their similarity scores. Score threshold laga sakte ho (e.g., >0.75 only)
  5. Chunks + original query = LLM prompt — Format: "Given this context: [chunks], answer this question: [query]. Only use information from the context."
  6. LLM grounded answer deta hai — answer directly context se aata hai, hallucination almost zero kyunki LLM ko explicitly bola gaya hai "sirf context se answer de"

Why it works: LLM ko hallucinate karne ki ZAROORAT nahi rehti. Answer already context mein pada hai — LLM bas summarize aur format karta hai. Yeh difference hai ek unreliable chatbot aur ek production-grade system mein.

🇮🇳 Indian Analogy: "Tu exam mein open book le jaata hai — woh open book hai tera Vector DB. Teacher (user) question poochta hai, tu book mein relevant page dhundhta hai (retrieval), aur phir answer likhta hai (generation). Bina book ke tu guess karega — aur guess galat bhi ho sakta hai!"

from langchain_community.document_loaders import PyPDFLoader, DirectoryLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_community.vectorstores import Chroma
from langchain.chains import RetrievalQA
from langchain.prompts import PromptTemplate
import os

# ---- CONFIGURATION ----
os.environ["OPENAI_API_KEY"] = "sk-your-key-here"

# Step 1: Document load karo — Multiple sources support
# USE CASE: HR department ke 50+ PDF policies load karo
loader = DirectoryLoader(
    "./hr_policies/",          # Folder jismein saare PDFs hain
    glob="**/*.pdf",           # Saare PDF files pick karo recursively
    loader_cls=PyPDFLoader,    # PDF parser use karo
    show_progress=True         # Progress bar dikhao (50 files hain, time lagega)
)
documents = loader.load()
print(f"Total pages loaded: {len(documents)}")  # e.g., "Total pages loaded: 342"

# IMPORTANT: Metadata add karo — production mein yeh ZAROOR chahiye
# Isse pata chalega answer KAUNSI file se aaya
for doc in documents:
    # File path se department extract karo
    if "leave" in doc.metadata["source"].lower():
        doc.metadata["department"] = "HR-Leave"
        doc.metadata["doc_type"] = "policy"
    elif "salary" in doc.metadata["source"].lower():
        doc.metadata["department"] = "HR-Compensation"
        doc.metadata["doc_type"] = "policy"
    doc.metadata["indexed_date"] = "2024-01-15"
    doc.metadata["version"] = "v2.1"

# Step 2: Chunking — bade documents ko chhote pieces mein todo
# WHY 1000 chars? Testing showed best retrieval quality at this size for policy docs
# WHY 200 overlap? Policy documents mein ek paragraph ka context next mein continue hota hai
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,      # Har chunk ki max size — tested for policy docs
    chunk_overlap=200,    # Overlap taaki context na tute — critical for adjacent sections
    length_function=len,  # Character count use karo
    separators=["\n\n", "\n", ". ", " ", ""],  # Pehle paragraph pe split, phir line pe
    add_start_index=True  # Start position track karo — debugging ke liye useful
)
chunks = text_splitter.split_documents(documents)
print(f"Total chunks: {len(chunks)}")  # e.g., "Total chunks: 1847"

# Step 3: Embeddings — text ko numbers mein convert karo
embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small",  # $0.02/1M tokens — production sweet spot
    # Dimensions reduce karo agar cost concern hai:
    # dimensions=512  # Quality slightly less, but 3x cheaper storage
)

# Step 4: Vector Store — Chroma for dev, Qdrant for production
vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    persist_directory="./chroma_hr_db",
    collection_name="hr_policies_v2"
)
print("Vector store created and persisted!")

# Step 5: Retriever — search strategy configure karo
retriever = vectorstore.as_retriever(
    search_type="mmr",           # MMR = relevance + diversity (avoids duplicate chunks)
    search_kwargs={
        "k": 5,                  # Top 5 results return karo
        "fetch_k": 20,           # Internally 20 candidates fetch karo, phir top 5 select
        "lambda_mult": 0.7       # 70% relevance, 30% diversity
    }
)

# Step 6: LLM setup — GPT-4 for accuracy, GPT-3.5 for speed/cost
llm = ChatOpenAI(
    model="gpt-4",
    temperature=0,        # 0 = deterministic — same question same answer (production requirement)
    max_tokens=500,       # Limit output length — cost control
    request_timeout=30    # 30 sec timeout — don't hang forever
)

# Step 7: Custom prompt — CRITICAL for quality answers
prompt_template = """Tu ek HR assistant hai. Tujhe neeche context diya gaya hai jo company ke official documents se hai.

RULES:
1. SIRF context ke basis pe answer de. Apne se kuch mat add kar.
2. Agar context mein answer nahi hai toh CLEARLY bol: "Is baare mein mujhe policy documents mein information nahi mili. Please HR team se contact karein."
3. Answer mein source document ka naam mention kar.
4. Hindi-English mix mein answer de (jaise office mein baat karte hain).
5. Agar policy dates ya numbers mention hain toh EXACTLY wahi use kar.

Context: {context}

Employee ka Question: {question}

Answer (with source):"""

prompt = PromptTemplate(template=prompt_template, input_variables=["context", "question"])

# Step 8: RAG Chain — sab connect karo
qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    chain_type="stuff",  # "stuff" = saare chunks ek prompt mein (best for <5 chunks)
    retriever=retriever,
    chain_type_kwargs={"prompt": prompt},
    return_source_documents=True  # Source documents bhi return karo — transparency
)

# Step 9: Query karo! — Real production query
result = qa_chain.invoke({"query": "Maternity leave kitne din ki milti hai aur kab se start hoti hai?"})
print(f"\n{'='*50}")
print(f"Answer: {result['result']}")
print(f"\nSources used:")
for i, doc in enumerate(result['source_documents'], 1):
    print(f"  {i}. {doc.metadata['source']} (Page {doc.metadata.get('page', 'N/A')})")
print(f"{'='*50}")

⚠️ Common Mistakes & How to Fix

  • Chunk size galat: Bahut bada (2000+) = irrelevant content bhi aa jaata hai, LLM confused hota hai. Bahut chhota (100) = context tut jaata hai, incomplete answers. Fix: Start with 500-1000, evaluate with real queries, tune iteratively.
  • Different embedding models: Document embed ek model se (e.g., OpenAI), query embed doosre se (e.g., Cohere) = vectors incompatible, similarity scores meaningless. Fix: ALWAYS use same model for both. If you change model, RE-INDEX everything.
  • k=1 rakhna: Sirf ek chunk se answer banana risky — what if that chunk is partially relevant? Fix: Minimum k=3, ideally k=4-5. More chunks = more context = better answers.
  • No metadata/source tracking: Production mein user poochega "yeh answer kahan se aaya?" Fix: ALWAYS store source file, page number, date in metadata.
  • Using chain_type="stuff" with 20 chunks: Token limit exceed ho jaayega! Fix: >5 chunks ke liye "map_reduce" ya "refine" use karo.

    """Har document mein rich metadata add karo"""
    for doc in documents:
        doc.metadata.update({
            "source_type": source_type,
            "department": department,

# ===== DATA CLEANING — VERY IMPORTANT =====
def clean_document(doc):
    """Document content ko clean karo — production quality ke liye"""
    text = doc.page_content
    text = re.sub(r'\s+', ' ', text)           # Multiple spaces → single space
    text = re.sub(r'\n{3,}', '\n\n', text)     # Too many newlines → max 2
    text = text.strip()                         # Leading/trailing whitespace
    text = re.sub(r'Page \d+ of \d+', '', text) # Remove page numbers
    text = re.sub(r'(?i)confidential', '[CONFIDENTIAL]', text)  # Flag sensitive content
    
    # Skip too short docs (likely garbage/headers)
    if len(text) < 50:
        return None  # Will be filtered out
    
    doc.page_content = text
    return doc

print(f"\nTotal documents after cleaning: {len(cleaned_docs)} (removed {len(all_documents) - len(cleaned_docs)} garbage docs)")

2.3 Chunking Strategy — Yeh Galat Ho Toh Sab Kuch Galat

Ek senior engineer ki taraf se — "Maine production mein 3 baar chunking strategy change ki hai. Har baar retrieval quality 20-30% improve hua. Yeh UNDERESTIMATED step hai."

🇮🇳 Analogy: "Tu ek kitaab ka summary banana chahta hai. Poori kitaab ek baar mein dega LLM ko = confused ho jaayega (context window bhi overflow ho sakta hai). Sirf ek line dega = no context, answer useless hoga. Chunking = sahi size ke pages banana — na bahut bade, na bahut chhote. Jaise Maggi ka packet — exact 2 min mein banta hai, zyada paani = tasteless, kam paani = kaccha. Chunking mein bhi exact sahi size = tasty answer."

Chunking RAG pipeline ka make-or-break step hai. Galat chunk size = irrelevant retrieval = hallucinated answer. Sahi chunk size = precise retrieval = accurate answer.

Key Insight: Chunk size decide karte waqt soch — "Is chunk ko AKELE padhke kya user ke question ka answer mil sakta hai?" Agar haan, toh size sahi hai. Agar chunk ka matlab samajhne ke liye surrounding text chahiye, toh overlap badhao ya chunk size badhao.

🎯 Chunking Strategy — Real Decision Making

Scenario 1: HR Policy Bot (Infosys)

Docs: Well-structured PDFs with clear sections. Decision: RecursiveCharacterTextSplitter(chunk_size=800, overlap=150). WHY: Policies have clear paragraphs, 800 chars usually covers one complete rule/clause.

Scenario 2: Legal Contract Analysis (Law firm)

Docs: 200-page contracts with complex language. Decision: SemanticChunker with percentile breakpoint. WHY: Legal language doesn't follow nice paragraph structure. Meaning-based splitting preserves clause integrity.

Scenario 3: API Documentation Bot (Developer tool)

Docs: Markdown with code examples. Decision: MarkdownHeaderTextSplitter + RecursiveCharacterTextSplitter. WHY: Split by headers first (each endpoint = one section), then split large sections further. Metadata preserves endpoint hierarchy.

Scenario 4: Code Search (GitHub Copilot alternative)

Docs: Python/JS source files. Decision: CodeTextSplitter(language=Language.PYTHON). WHY: Splits at function/class boundaries. Each chunk = one complete function with docstring. Searching "how to handle authentication" finds the auth function.

Scenario 5: Customer Support (E-commerce)

Docs: FAQ database (short Q&A pairs). Decision: DON'T chunk! Each FAQ entry is already a perfect "chunk". Load as-is. WHY: Chunking FAQ entries would break Q&A pairs.

📏 Chunk Size Decision Guide — Use This in Production

  • • 128-256 tokens: Factoid queries — "CEO kaun hai?" "Office ka address?" "Price kya hai?" — Short, specific answers from small chunks
  • • 256-512 tokens: General RAG — "Leave policy explain karo" "Refund process batao" — Most common use case
  • • 512-1024 tokens: Complex analysis — "In 3 policies compare karo" "Detailed process explain karo" — Need more context per chunk
  • • 1024-2048 tokens: Summarization tasks — "Is chapter ka summary do" — Only when LLM needs full context. Costly!

    CharacterTextSplitter,

    Language,
    RecursiveCharacterTextSplitter as CodeSplitter,

# ===== Strategy 1: RecursiveCharacterTextSplitter (DEFAULT — Use 80% of time) =====
# USE CASE: Company policy documents, blog posts, general text
# HOW: Tries to split on \n\n first, then \n, then ". ", then " ", then ""
recursive_splitter = RecursiveCharacterTextSplitter(
    chunk_size=800,        # Sweet spot for policy docs (tested!)
    chunk_overlap=150,     # 15-20% overlap is ideal
    length_function=len,
    separators=["\n\n", "\n", ". ", " ", ""],
    add_start_index=True   # Track position — useful for highlighting in UI
)

# chunk_size=800: One complete policy clause usually fits in 600-900 chars
# chunk_overlap=150: If a sentence is split, overlap ensures context continuity
# separators: Prefers paragraph breaks (semantic boundaries) over random character splits

# ===== Strategy 2: TokenTextSplitter (When token budget is tight) =====
# USE CASE: You have GPT-3.5 (4K context), need to fit 5 chunks + prompt + answer
# If each chunk = 300 tokens, 5 chunks = 1500 tokens, prompt = 500, answer = 500 → fits in 4K!
token_splitter = TokenTextSplitter(

# ===== PRO TIP: Contextual Chunking =====
def add_contextual_header(chunks, doc_title, doc_summary):
    """Har chunk ke start mein document context add karo"""
    for i, chunk in enumerate(chunks):
        context_header = f"[From: {doc_title}]\n[Summary: {doc_summary}]\n[Chunk {i+1}/{len(chunks)}]\n\n"
        chunk.page_content = context_header + chunk.page_content
        chunk.metadata["chunk_index"] = i
        chunk.metadata["total_chunks"] = len(chunks)
        chunk.metadata["has_context_header"] = True
    return chunks
# WHY: When a chunk is retrieved alone, it now has context about WHICH document it's from
# This helps LLM understand the chunk better even without other chunks

2.4 Embeddings — Numbers Mein Meaning

Ek senior engineer ki taraf se — "Embedding samajh liya toh RAG ka 50% samajh gaya. Yeh wo bridge hai jo human language ko machine math mein convert karta hai."

What is an Embedding: Embedding matlab text ko ek list of numbers (vector) mein convert karna. "Happy" = [0.2, 0.8, -0.1, ...] aur "Joyful" = [0.21, 0.79, -0.08, ...] — dekh, similar meaning = similar numbers! Yeh numbers typically 1536 ya 3072 dimensions ke hote hain. Har dimension ek "aspect of meaning" capture karta hai — though kaunsa dimension kya capture karta hai, woh human-interpretable nahi hai.

King - Man + Woman = Queen: Yeh classic example hai. Embeddings sirf similarity nahi, RELATIONSHIPS bhi capture karte hain. "King" ka vector mein se "Man" ka vector minus karo aur "Woman" add karo = "Queen" ke paas pahunch jaoge. Iska matlab embeddings language ke deep patterns samajhte hain — gender, tense, plurality, profession, sab encode hota hai in numbers mein.

🇮🇳 Analogy: "Soch ki embedding ek GPS coordinate hai. 'Dilli' aur 'New Delhi' ka coordinate almost same hoga (same jagah). 'Dilli' aur 'Noida' thoda door hoga (nearby but different). 'Dilli' aur 'Mumbai' bahut door hoga (different cities). 'Dilli' aur 'Samosa' — completely different plane pe hai! Vector DB mein search = 'Mere GPS ke sabse paas kaun hai?'"

Distance Metrics — Kaise Compare Karte Hain Vectors Ko:

Cosine Similarity

Direction compare karta hai, magnitude (length) nahi. Do vectors ke beech ka angle measure karta hai. Best for text — kyunki document length se affect nahi hota. 1000-word doc aur 100-word doc same topic pe → high cosine despite different lengths.

Range: -1 to 1. 1 = identical direction, 0 = unrelated, -1 = opposite.

✅ DEFAULT choice for RAG — almost always use this

Euclidean Distance (L2)

Actual spatial distance — straight line between two points. Magnitude sensitive — long document vectors will be "further" from short doc vectors even if same topic. Needs normalized vectors for fair comparison.

Range: 0 to ∞. 0 = identical, higher = more different.

Use when: vectors are already normalized, spatial distance matters

Dot Product (Inner Product)

Magnitude + direction dono consider karta hai. Very fast computation (just multiply and add). On normalized vectors, equals cosine similarity. Used internally by many vector DBs for speed.

Range: -∞ to +∞. Higher = more similar.

Use when: speed critical, vectors pre-normalized

# ===== Similarity Calculation — Understanding the Math =====
def cosine_similarity(vec1: List[float], vec2: List[float]) -> float:
    """Cosine similarity — 1 = identical meaning, 0 = unrelated, -1 = opposite"""
    a, b = np.array(vec1), np.array(vec2)
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

def euclidean_distance(vec1: List[float], vec2: List[float]) -> float:
    """Euclidean distance — 0 = identical, higher = more different"""
    return float(np.linalg.norm(np.array(vec1) - np.array(vec2)))

2.5 Vector Stores — Production Decision Guide

Internal Index Types (How search is fast):

  • HNSW (Hierarchical Navigable Small World): Graph-based. Imagine a highway system — you start at a random city, each city has connections to neighbors AND far-away cities. You navigate through connections to reach destination fast. O(log n) search time. Production default for most stores.
  • IVF (Inverted File Index): Cluster-based. First, divide all vectors into 100 clusters (like postal codes). On search, first find which cluster is closest to query, then search only within that cluster. Less memory than HNSW but slightly less accurate.
  • Flat (Brute Force): Compare query against EVERY stored vector. O(n). Exact results, zero approximation. But impossibly slow at scale (1M vectors = 1M comparisons per query). Only for <10K vectors or testing.

3.1 Retrieval Techniques — Smart Search

MMR (Maximal Marginal Relevance)

Problem: Pure similarity search mein top 5 results almost same content ke hote hain (duplicates). Agar tera document mein "leave policy" 5 jagah repeat hua hai, toh top 5 results = same policy ka 5 versions. User ko koi naya info nahi milta.

How MMR works internally: Pehle fetch_k=20 candidates lao (all by similarity). Phir iteratively select: pick highest similarity wala → next pick high similarity BUT also different from already selected ones. Lambda parameter controls: 1.0 = pure relevance (like normal search), 0.0 = pure diversity (most different from each other). Sweet spot: 0.5-0.7

Real Use Case: Research Paper Discovery

Researcher searches "transformer architecture improvements". Without MMR: 5 results all about attention mechanism. WITH MMR: 1 about attention, 1 about positional encoding, 1 about efficiency, 1 about multimodal, 1 about training tricks. MUCH more useful!

✅ When to use: Research tasks, broad topics, when diverse perspectives needed

❌ When NOT: Specific factoid queries ("CEO ka naam?"), when you WANT redundancy for confidence

Hybrid Search (Dense + Sparse)

The Problem: Dense (vector) search understands MEANING but misses exact keywords. "Find document about RFC-7231" — vector search might find HTTP-related docs but miss the exact RFC number. Sparse (BM25) matches KEYWORDS perfectly but doesn't understand meaning. "Find document about return policy" — BM25 won't find docs that say "refund process" (different words, same meaning).

Solution: Combine both! EnsembleRetriever with weights. alpha=0.5 means 50% vector + 50% keyword. For technical docs (code, specifications, proper nouns) → more keyword weight (0.6-0.7). For general text → more semantic weight (0.3-0.4 keyword).

Real Use Case: Technical Documentation Search (AWS docs)

Engineer searches "S3 bucket policy for cross-account access with arn:aws:s3:::my-bucket/*". Vector search alone won't match the exact ARN pattern. BM25 alone won't understand "cross-account access" context. Hybrid catches both — the exact ARN keyword AND the cross-account access concept.

✅ When to use: Technical docs, code search, queries with proper nouns/IDs/versions

❌ When NOT: Purely conversational queries, when all docs use same terminology

Re-Ranking (Two-Stage Retrieval)

The Problem: Bi-encoder (embedding model) embeds query and document SEPARATELY then compares. Fast (can search millions) but misses nuances of query-document interaction. Cross-encoder processes query+document TOGETHER — understands relationships much better but is SLOW (can't run on million docs).

Solution — Two Stage: Stage 1 (fast, approximate): Bi-encoder retrieves top-20 candidates from millions in 50ms. Stage 2 (slow, accurate): Cross-encoder re-ranks those 20 candidates → picks best 5. Total time: ~200ms (acceptable for production).

Real Use Case: Legal Document Retrieval

Lawyer searches "cases where court upheld right to privacy despite national security argument". Stage 1 retrieves 20 privacy-related cases. Stage 2 (cross-encoder) deeply analyzes each: "Is national security argument present? Did court still uphold privacy?" → Returns only 5 truly relevant cases. Without re-ranking, 3 of top 5 would be irrelevant.

✅ When to use: High-stakes (legal, medical), complex queries, when precision > speed

❌ When NOT: Real-time chat (latency critical), simple factoid queries, low-budget deployments

Multi-Query Retriever

The Problem: User's single query might not capture all angles. "Tell me about employee benefits" — this one query might miss dental insurance (different wording), remote work allowance (different category), gym membership (different section).

Solution: LLM generates 3-5 query variations automatically. Each variation searches separately. Results combined + deduplicated. Coverage dramatically increases — what one query misses, another catches.

Real Use Case: E-commerce Product Search

User: "comfortable shoes for standing all day". LLM generates: "ergonomic footwear for prolonged standing" + "cushioned shoes for nurses/doctors" + "arch support shoes for office work" + "anti-fatigue insoles and shoes". Each finds different products → combined result is comprehensive.

✅ When to use: Ambiguous queries, broad topics, when recall matters more than precision

❌ When NOT: Specific factoid queries, latency-critical (3-5x more searches), cost-sensitive

Parent Document Retriever

The Dilemma: Small chunks (200 chars) → excellent retrieval precision (finds exact relevant sentence). BUT LLM gets too little context to generate good answer. Large chunks (2000 chars) → LLM has rich context. BUT retrieval becomes imprecise (chunk has relevant + irrelevant mixed).

Solution: Store SMALL chunks for search (precise targeting), but when a small chunk matches, return its PARENT (large chunk) to LLM. Best of both worlds! InMemoryStore maintains the parent-child mapping.

Real Use Case: Medical Knowledge Base

Doctor searches "metformin contraindications". Small chunk (200 chars) precisely matches: "Metformin is contraindicated in patients with eGFR below 30." But to give a useful answer, LLM needs the full section (2000 chars): contraindications + dosage adjustments + monitoring requirements + alternative drugs. Parent retriever gives BOTH precision and context.

✅ When to use: When context around the match is as important as the match itself

❌ When NOT: FAQ-style docs where each entry is self-contained, simple Q&A pairs

3.2 Advanced RAG Patterns — Production Arsenal

Pattern 1: RAG Fusion

What: Generate multiple query variations → search each independently → merge results using Reciprocal Rank Fusion (RRF) → best combined results go to LLM.

Why: Single query has single perspective. "Machine learning deployment challenges" misses docs about "model serving issues", "inference latency problems", "ML ops pain points" — all related but different wording.

How RRF works: For each document, score = sum of 1/(k + rank) across ALL query results. Documents that appear in MULTIPLE queries get higher combined score. k=60 is standard constant (dampens top-rank bias).

🏢 Real Use Case: Customer Insights Platform (PhonePe/Razorpay)

Scenario: Product manager asks: "What are users saying about our new checkout flow?"

Pattern 2: Corrective RAG (CRAG)

What: Retrieve → Grade each document (relevant or not?) → If irrelevant: fallback to web search or rephrase query → Generate only from verified relevant docs.

Why: Basic RAG BLINDLY trusts retrieval. If vector DB returns garbage (outdated doc, wrong topic), LLM will confidently generate wrong answer from that garbage. CRAG adds a "quality gate" — only verified relevant docs reach LLM.

How Grading Works: LLM (or smaller classifier) reads each retrieved document + original query, decides: "Is this document actually relevant to answering this question?" YES → keep. NO → discard. If all discarded → web search fallback.

Problem without CRAG: Vector DB has old 2022 regulation docs. Retrieves outdated info. Bot confidently gives WRONG margin requirements. User loses money.

  1. Retrieve top-5 docs from knowledge base
  2. Grade each: "Is this about April 2024 F&O margin changes?" → 2022 docs marked IRRELEVANT
  3. Only 1 doc relevant (but not comprehensive enough)
  4. Trigger web search fallback → finds latest SEBI circular from official website
  5. Combine internal doc + web result → generate answer with proper citation
  6. Flag to user: "Note: This includes information from SEBI website as our knowledge base may not be fully updated."

Impact: Zero wrong financial advice. User trust maintained. Regulatory compliance assured.

✅ When to use: Critical accuracy needed (finance, legal, medical), knowledge base may be outdated, trust is paramount

Pattern 3: Self-RAG (Self-Reflective RAG)

What: Agent evaluates itself at every step: "Should I retrieve? Are docs relevant? Is my answer faithful to context? Is my answer useful?" 4 reflection checkpoints in one pipeline.

Why: CRAG only checks retrieval quality. Self-RAG also checks GENERATION quality. Even with perfect retrieval, LLM might still: (a) ignore the context and hallucinate, (b) generate irrelevant answer, (c) misinterpret the documents. Self-RAG catches ALL these failures.

4 Reflection Tokens:

  • Retrieve: "Do I need to search for information, or can I answer directly?"
  • ISREL: "Is this retrieved document relevant to the question?"
  • ISSUP: "Is my generated answer SUPPORTED by the retrieved context? Or did I hallucinate?"
  • ISUSE: "Is my answer actually USEFUL to the user? Does it address their need?"

🏢 Real Use Case: Healthcare Clinical Decision Support

Scenario: Doctor asks: "Can I prescribe ibuprofen for this patient with stage 3 CKD and history of GI bleeding?"

  1. Retrieve check: "Yes, this needs retrieval — drug interaction + patient condition specific"

  3. ISREL check: All 3 docs relevant ✓
  4. Generate: "Ibuprofen should be avoided due to CKD + GI history. Consider acetaminophen..."
  5. ISSUP check: "Is this SUPPORTED by retrieved docs?" → Yes, docs explicitly mention NSAID contraindication ✓
  6. ISUSE check: "Did I answer the question AND provide alternative?" → Yes ✓
  7. Final answer delivered with citations to specific guidelines

If ISSUP fails (hallucinated drug interaction): System regenerates with stricter "only state what documents explicitly say" prompt. NEVER delivers unverified medical info.

❌ When NOT: Casual chatbots, speed-critical apps (multiple LLM calls per query = slow + expensive), simple FAQ bots

What: Classify query complexity FIRST → route to appropriate pipeline. Simple questions → direct LLM (skip retrieval). Medium → basic RAG. Complex → full advanced RAG. Ambiguous → web search + RAG.

Why: Not every query needs the full RAG pipeline. "What is 2+2?" doesn't need vector search! But "What was our Q3 revenue compared to Q2?" definitely does. Adaptive RAG saves 40-60% cost by skipping unnecessary retrieval for simple queries.

Agentic AI

RAG ek tool hai. Agent ek ENGINEER hai jo tools use karta hai, plan banata hai, aur iterate karta hai 🤖

4.1 Agent Kya Hota Hai — Full Architecture with Use Cases

Ek senior engineer ki taraf se — "Agar RAG ek Google Search hai, toh Agent ek intern hai jisko tu task de sakte ho aur woh khud figure out karta hai kaise karna hai. But unlike intern, agent tireless hai aur 24/7 available."

Core Difference — RAG vs Agent:

RAG (One-Shot Pipeline)

Query → Retrieve → Answer → DONE

Fixed pipeline. No decision-making. No iteration. Always same steps regardless of query. Can't call external APIs. Can't take actions. Just search and answer.

Agent (Autonomous Loop)

Query → Think → Plan → Act → Observe → Think → Act → ... → Answer

Dynamic decisions at every step. Can use multiple tools. Iterates until satisfied. Handles failures. Adapts strategy based on intermediate results.

🇮🇳 Analogy: "RAG = Swiggy delivery. Tu order de, woh laake de, done. No questions asked. Agent = Personal chef. Pehle poochta hai 'kya khana hai? spicy level? budget?', phir recipe plan karta hai, market jaata hai (tool call), ingredients check karta hai, nahi mila toh alternative dhundhta hai (error handling), cook karta hai, taste karta hai (self-evaluation), adjust karta hai, phir serve karta hai. Agar tu bolta hai 'thoda aur namak' — woh sudhar deta hai (iteration)!"

5 Components of an Agent (Each Explained):

1. LLM as Reasoning Engine (The Brain)

Agent ka CORE. Yeh decide karta hai: "Kya karna chahiye next? Kaunsa tool use karun? Kya result expected tha? Kya mujhe approach change karna chahiye?" GPT-4 / Claude use hota hai for complex reasoning. Temperature = 0 for consistent decisions.

Real-world: GPT-4 for complex agents, GPT-3.5 for simple tool-calling agents (cheaper)

2. Tools (The Hands)

LLM sirf text generate karta hai. Tools se woh ACTUALLY kaam kar sakta hai: database query, API call, email send, code run, file create, search internet. Each tool = ek Python function + JSON schema (name, description, parameters). LLM schema padhke samajhta hai kab kaunsa tool use karna hai.

Real-world: RAG tool + web search + calculator + email + CRM API + code execution

3. Memory (The Diary)

Short-term: Current conversation (what user said, what agent did). Long-term: Past interactions across sessions (user preferences, past decisions). Episodic: "Pichhli baar yeh approach try kiya tha, fail hua tha — iss baar doosra try karun." Without memory = goldfish. Every conversation is fresh start.

Real-world: ConversationBufferMemory for chat, Vector DB for long-term, mem0 for automatic memory management

4. Planning (The Strategy)

Complex task ko steps mein todna. "Research report likhna hai" → "Pehle web search, phir key points extract, phir outline banao, phir write each section, phir review." ReAct pattern = plan one step at a time. Plan-and-Execute = plan all steps upfront, then execute sequentially.

Real-world: ReAct for dynamic tasks, Plan-Execute for predictable multi-step workflows

5. Observation Loop (Learning from Actions)

Har action ke baad result OBSERVE karo. "API call fail hua — kya error aaya? Timeout? Auth failure? Rate limit?" Based on observation: retry, change approach, or report failure. This loop makes agents ADAPTIVE — they recover from failures instead of crashing.

Real-world: Error handling, retry logic, fallback strategies, self-correction

5.1 LangGraph — Why & When

Ek senior engineer ki taraf se — "Simple chains = junior developer's first project. LangGraph = senior developer's production system. Jab tujhe loops, conditionals, error recovery, state management chahiye — LangGraph is the answer."

Why LangGraph over simple chains:

  • Loops: Agent needs to retry until success. Simple chain = one shot. LangGraph = "keep trying until answer is good".
  • Branching: If query is simple → route A. If complex → route B. If out of scope → route C. Dynamic decision-making.
  • State Management: Share information between steps. "Step 3 needs output of Step 1 + Step 2 combined."
  • Human-in-the-Loop: Pause execution, wait for human approval, then continue. Critical for financial transactions, content publishing.
  • Persistence: Save graph state to DB. Resume later. Handle server restarts gracefully.

🇮🇳 Analogy: "Simple chain = straight road from A to B. No turns, no choices. LangGraph = Google Maps navigation. Multiple routes, traffic pe adjust karo, roadblock aaye toh reroute karo, passenger ko batao 'should I take toll road?' (human-in-the-loop), destination pe pahunchao."

# ===== STATE: Shared data between all nodes =====
class AgentState(TypedDict):

@tool
def check_system_status(service_name: str) -> str:
    """Check if a service/system is up or down.

def search_it_knowledge_base(query: str) -> str:

    # Production: actual RAG search
    solutions = {

    return "end"  # Final answer ready — END

tool_node = ToolNode(tools)

workflow = StateGraph(AgentState)
workflow.add_node("agent", agent_node)       # Reasoning node
workflow.add_node("tools", tool_node)         # Tool execution node
workflow.set_entry_point("agent")             # Start here

# Conditional: agent decides — tools ya end?
workflow.add_conditional_edges("agent", should_continue, {"tools": "tools", "end": END})
# After tools execute, go back to agent (loop!)
workflow.add_edge("tools", "agent")

# Compile — now it's runnable!
app = workflow.compile()

# ===== RUN IT =====
result = app.invoke({
    "messages": [HumanMessage(content="Bhai mera VPN bahut slow chal raha hai. Bangalore office se connect kar raha hoon. Kya issue hai?")]
})
# Agent will:
# 1. THINK: "VPN issue hai, pehle status check karun"
# 2. ACT: check_system_status("vpn") → "DEGRADED"
# 3. OBSERVE: VPN is slow for Bangalore office
# 4. THINK: "Status confirms issue. Let me find a fix"

6.1 Token Budgeting & Cost Control

🏢 Real Use Case: SaaS chatbot handling 10,000 queries/day

Problem: First month bill = ₹1.5 lakh! Budget was ₹30K. Without token budgeting, 70% of tokens were wasted on irrelevant context chunks being sent to LLM.

Solution Applied:

  • Re-rank before sending (top 3 instead of top 8 chunks) → 60% token reduction
  • Contextual compression (extract only relevant sentences from chunks) → 40% further reduction
  • Adaptive RAG (skip retrieval for simple greetings/thanks — 30% of queries) → 30% queries cost ₹0
  • Semantic cache (same/similar questions get cached answer) → 45% queries served from cache

Result: Monthly cost ₹1.5L → ₹25K. Better answers AND cheaper!

# ========================================
# Token Budget Management — Production Cost Control
# ========================================
import tiktoken

def count_tokens(text: str, model: str = "gpt-4") -> int:
    """Token count karo — har API call se pehle check karo budget"""
    encoding = tiktoken.encoding_for_model(model)
    return len(encoding.encode(text))

def calculate_query_cost(prompt_tokens: int, completion_tokens: int, model: str = "gpt-4") -> float:
    """Ek query ka cost calculate karo in USD"""
    pricing = {
        "gpt-4": {"input": 0.03/1000, "output": 0.06/1000},           # $30/1M input
        "gpt-4-turbo": {"input": 0.01/1000, "output": 0.03/1000},     # $10/1M input
        "gpt-3.5-turbo": {"input": 0.0005/1000, "output": 0.0015/1000}, # $0.5/1M input
    }
    p = pricing.get(model, pricing["gpt-4"])
    return prompt_tokens * p["input"] + completion_tokens * p["output"]

def fit_chunks_to_budget(chunks, max_context_tokens=3000, model="gpt-4"):
    """Chunks ko token budget mein fit karo — priority order mein (already ranked)"""
    selected = []
    current_tokens = 0
    for chunk in chunks:  # Assume chunks already sorted by relevance score
        chunk_tokens = count_tokens(chunk.page_content, model)
        if current_tokens + chunk_tokens <= max_context_tokens:
            selected.append(chunk)
            current_tokens += chunk_tokens
        else:
            break  # Budget full!
    print(f"Selected {len(selected)}/{len(chunks)} chunks using {current_tokens}/{max_context_tokens} tokens")
    return selected

# GPT-4 with 8K context window:
# System prompt: ~300 tokens (keep it TIGHT)
# Retrieved context: ~3000 tokens (4-6 chunks @ 500-700 tokens each)
# User query + history: ~700 tokens
# Reserved for output: ~1000 tokens (answer)
# TOTAL: 5000/8000 tokens used — 3000 buffer for safety

from langchain.globals import set_llm_cache

# Simple: exact match cache

# → Semantic similarity > 0.9 → serve cached answer! Zero LLM cost.

6.4 Security & Access Control

🏢 Real Use Case: Multi-tenant SaaS with role-based document access

Scenario: Company has 3 levels: Public docs (all employees), Internal (department-specific), Confidential (leadership only). Without security, a junior engineer could ask "What is the CEO's salary package?" and RAG would happily answer from confidential HR docs.

Security Layers Implemented:

  • Input Validation: Detect prompt injection attempts ("ignore previous instructions...", "reveal system prompt...")
  • Role-Based Retrieval: Engineer can only search public + engineering docs. HR can search HR + public. CEO can search everything.
  • Output Filtering: Even if something slips through, check output for PII (Aadhaar, PAN, phone numbers) before sending to user.
  • Audit Trail: Every query + response logged with user identity. Compliance requirement for SEBI/RBI regulated companies.

6.5 Scaling RAG — From 1K to 10M Documents

🏢 Real Use Case: E-commerce with 10M product descriptions + 50M reviews

Challenges at Scale:

  • 10M documents × 5 chunks each = 50M vectors. Single Chroma instance can't handle this.
  • 1000 concurrent users searching = need distributed search across multiple nodes.
  • New products added hourly = real-time indexing pipeline needed, not batch.
  • Cost: 50M vectors × 1536 dims × 4 bytes = ~300GB storage just for vectors!

Production Architecture:

  • Qdrant Cloud with 3 replicas (handle concurrent reads) + sharding (split data across nodes)
  • Redis for semantic caching (40% queries are repeated) + rate limiting
  • Kafka for async indexing pipeline (product added → message → background worker embeds → indexed)
  • LangServe for serving RAG chain as REST API with load balancing
  • Quantized embeddings (int8 instead of float32) → 75% storage reduction with 1% quality loss

Result: P95 latency 200ms, handles 5000 RPS, monthly cost $3K (vs $15K without optimization)
